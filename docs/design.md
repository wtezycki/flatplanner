# Flatplanner: implementation design

Implementation specification: architecture, data model, normalization, API, LLM usage, frontend, deploy, tests and order of work.

As of 2026-11-05. **AI-first pivot: section 16 supersedes the parts of sections 5–7, 9, 12–14 it names.**

**Scope:** features from [product-scope.md](product-scope.md) §4, broken down into 17 implementation items in §13. Feature identifiers (UC1–UC17, W1–W8, e.g. mini-W2 = fact extraction from descriptions) are defined in the table in [product-scope.md](product-scope.md). Names (tables, columns, types, endpoints, JSON fields, environment variables) are final and are copied 1:1.

**Language:** this document is in English; **the user interface and every text generated by the API** (enum labels, chips, summary, `why`, notices, blockers, warnings, `askSeller`, fallback banner, error messages) **are in Polish**. English strings in the examples below are glosses; the canonical Polish texts are in [ui-spec.md](ui-spec.md) §7.

**Data scope:** **Tricity (Trójmiasto)** (Gdańsk, Gdynia, Sopot), flat sales. Scenarios A and B run on Gdańsk (rationale: [scraping-plan.md](scraping-plan.md) §2).

**Source of the data shape:** the JSON paths in section 4 were checked on 2026-11-04 against 14 live listings from Gdańsk and against results pages for Gdańsk, Gdynia and Sopot. The `data/raw/` directory is created only on the first import.

## 1. Overview

```
 LOCAL                                                       PRODUCTION (Railway)
 ┌──────────────────────┐  ┌──────────────┐  mysqldump     ┌──────────────┐   ┌───────────────────────────┐   HTTPS   ┌────────────┐
 │ Flatplanner.Ingest   │─▶│ local MySQL  │──(data)──────▶│ MySQL prod   │◀──│ Flatplanner.Api + SPA     │◀─────────▶│ browser    │
 │ scrape→normalize→    │  │ (compose)    │  import        │              │   │ (1 container, wwwroot)    │           └────────────┘
 │ enrich (LLM)→report  │  └──────────────┘                └──────────────┘   └─────────────┬─────────────┘
 └─────────┬────────────┘                                                                    │ only POST /api/search/interpret
           │ mini-W2 (import)                                                                ▼
           └──────────────────────────────▶ OpenAI Chat Completions API ◀────────────────────┘
```

- **Flatplanner.Ingest:** console app run locally. Fetches listings from otodom, normalizes them, enriches descriptions with an LLM (parking, storage unit) and prints a report.
- **Local MySQL:** working database for the import (`docker compose`).
- **mysqldump → import:** the only path for data to production. Transfers only the `listings` and `listing_facts` tables.
- **MySQL prod:** the schema is created by migrations run at API startup, the data comes from the import.
- **Flatplanner.Api:** Minimal API. It also serves the built SPA (static files + fallback to `index.html`), so CORS does not exist.
- **OpenAI API:** at runtime only the interpretation of the chatbox query calls it, behind a rate limiter and a hard spend limit at the provider.

**Why so many projects:** there are two executable processes (API on the server, Ingest locally) that share the `DbContext`, migrations, `SearchIntent` and the LLM client. The fourth project is the tests.
- **Fewer projects** (Ingest as a command in the API) push the scraper and its dependencies into the production image. In addition, migrations would have to be invoked from the web project.
- **More projects** (separate Domain, Infrastructure, Application) are layers without a second implementation, i.e. overengineering, which the task forbids.

There are no layers inside the projects: `DbContext` is used directly, without repositories and without MediatR.

## 3. Data model

### 3.1 Charset, collation, conventions

- Database and all tables: `utf8mb4` / `utf8mb4_0900_ai_ci`. In EF Core: `modelBuilder.HasCharSet("utf8mb4", DelegationModes.ApplyToAll).UseCollation("utf8mb4_0900_ai_ci", DelegationModes.ApplyToAll)` (compiled with Pomelo 9.0.0).
- The connection string always has `CharSet=utf8mb4`. Pomelo gets an explicit server version `ServerVersion.Parse("8.4.0-mysql")` (constant `DbConstants.ServerVersion` in Core), without `AutoDetect`, because the latter connects to the database already while the model is being built.
- Diacritic-free search does **not** rely on the collation (in UCA “ł” has no decomposition). It is done by the `search_text` column, normalized in C# (3.5).
- Dates: `DATETIME(6)` in UTC, in C# `DateTime` with `Kind=Utc`.
- Columns are snake_case via the `[Column("...")]` attribute on entities. Entities: `RawListing`, `Listing`, `ListingFact`. Context: `FlatplannerDbContext`.
- Enums are `VARCHAR` with constant values in C# (`static class Market { public const string Primary = "primary"; ... public static readonly string[] All = [...]; }`), without C# `enum` types. Thanks to this, no EF converters or `JsonStringEnumConverter` are needed.
- `JSON` columns are mapped in C# to `string[]` via `HasConversion` (System.Text.Json) with a `ValueComparer` based on `SequenceEqual`.

### 3.2 DDL (template for the `Initial` migration)

The migration must match **semantically**: the same table and column names, nullability, `JSON`, `utf8mb4`, unique keys, CHECK and FK. Exact numeric types (`TINYINT` vs `INT`) and text types (`MEDIUMTEXT` vs `LONGTEXT`) are left to the default EF/Pomelo mappings; explicit `HasColumnType` only for `JSON` and `DECIMAL`. Reproducing types 1:1 costs agent time with no gain at ~150 rows.

```sql
CREATE TABLE raw_listings (

  source           VARCHAR(16)   NOT NULL,             -- 'otodom'
  external_id      VARCHAR(32)   NOT NULL,             -- ad.id as a string
  url              VARCHAR(512)  NOT NULL,             -- ad.url
  fetched_at       DATETIME(6)   NOT NULL,
  ad_json          JSON          NOT NULL,             -- props.pageProps.ad WITHOUT keys with contact data (4.1)
  normalize_status VARCHAR(16)   NULL,                 -- accepted | rejected | NULL = not normalized yet
  reject_reason    VARCHAR(64)   NULL,                 -- code from 4.3, when rejected
  UNIQUE KEY ux_raw_listings_source_external (source, external_id)
);

CREATE TABLE listings (
  id                   BIGINT        NOT NULL AUTO_INCREMENT PRIMARY KEY,
  source               VARCHAR(16)   NOT NULL,
  external_id          VARCHAR(32)   NOT NULL,
  url                  VARCHAR(512)  NOT NULL,
  title                VARCHAR(300)  NOT NULL,
  description_text     MEDIUMTEXT    NOT NULL,         -- plain text (4.2); what the LLM sees and what search and anchors use
  description_markup   MEDIUMTEXT    NULL,             -- the same text with bold and italic kept as `**` and `*` (4.2, R23); the UI shows this
  search_text          MEDIUMTEXT    NOT NULL,         -- 3.5
  city_slug            VARCHAR(16)   NOT NULL,         -- gdansk | gdynia | sopot
  district_slug        VARCHAR(80)   NULL,             -- last segment of the reverseGeocoding id, e.g. 'wrzeszcz-gorny'
  district_name        VARCHAR(120)  NULL,             -- 'Wrzeszcz Górny'
  street               VARCHAR(160)  NULL,
  lat                  DECIMAL(9,6)  NOT NULL,
  lng                  DECIMAL(9,6)  NOT NULL,
  location_approximate TINYINT(1)    NOT NULL,         -- mapDetails.radius > 0
  price_pln            INT           NOT NULL,
  area_m2              DECIMAL(7,2)  NOT NULL,
  price_per_m2         INT           NOT NULL,         -- ROUND(price_pln / area_m2), computed by us
  rooms                TINYINT       NOT NULL,
  floor                TINYINT       NULL,             -- ground floor = 0, semi-basement = -1, floor_higher_10 = 11
  building_floors      TINYINT       NULL,
  build_year           SMALLINT      NULL,
  market               VARCHAR(16)   NOT NULL,         -- primary | secondary
  finish_condition     VARCHAR(24)   NULL,             -- ready_to_use | to_completion | to_renovation
  ownership            VARCHAR(24)   NULL,             -- full_ownership | limited_ownership
  heating              VARCHAR(24)   NULL,             -- urban | gas | boiler_room | electrical (R24)
  building_type        VARCHAR(24)   NULL,             -- block | apartment | tenement (R24)
  windows_type         VARCHAR(24)   NULL,             -- plastic | wooden | aluminium (R24)
  building_material    VARCHAR(24)   NULL,             -- brick | silikat | breezeblock | concrete_plate | concrete | cellular_concrete | reinforced_concrete | other (R24)
  rent_pln             INT           NULL,             -- Rent <= 0 -> NULL
  has_lift             TINYINT(1)    NULL,             -- 1 or NULL ("no information"); never 0
  has_balcony          TINYINT(1)    NULL,             -- as above
  has_garage           TINYINT(1)    NULL,             -- as above (garage/parking space marked in the advertisement)
  has_basement         TINYINT(1)    NULL,             -- as above (cellar marked in the advertisement)
  advertiser_type      VARCHAR(16)   NULL,             -- agency | private
  image_urls           JSON          NOT NULL,         -- string[] max 10, CDN URLs (size "medium")
  quality_flags        JSON          NOT NULL,         -- string[] (3.6)
  facts_status         VARCHAR(16)   NOT NULL DEFAULT 'pending',  -- pending | done | skipped | failed (section 5)
  created_at_source    DATETIME(6)   NOT NULL,
  scraped_at           DATETIME(6)   NOT NULL,         -- = raw_listings.fetched_at
  UNIQUE KEY ux_listings_source_external (source, external_id),
  KEY ix_listings_city_district (city_slug, district_slug),
  KEY ix_listings_created (created_at_source),
  CONSTRAINT ck_listings_has_lift     CHECK (has_lift     IS NULL OR has_lift     = 1),
  CONSTRAINT ck_listings_has_balcony  CHECK (has_balcony  IS NULL OR has_balcony  = 1),
  CONSTRAINT ck_listings_has_garage   CHECK (has_garage   IS NULL OR has_garage   = 1),
  CONSTRAINT ck_listings_has_basement CHECK (has_basement IS NULL OR has_basement = 1)
);

CREATE TABLE listing_facts (                         -- result of mini-W2, one row per (listing, fact)
  id                BIGINT        NOT NULL AUTO_INCREMENT PRIMARY KEY,
  listing_id        BIGINT        NOT NULL,
  fact_key          VARCHAR(16)   NOT NULL,          -- parking | storage
  status            VARCHAR(16)   NOT NULL,          -- included | extra_cost | not_available
  amount_pln        INT           NULL,              -- only for extra_cost, when the amount is in the quote

  validation_status VARCHAR(16)   NOT NULL,          -- accepted | rejected
  reject_reason     VARCHAR(32)   NULL,              -- missing_quote | quote_not_found | amount_not_in_quote | amount_out_of_range

```

**No FK** from `listings` → `raw_listings`: production does not get `raw_listings` (the raw JSON is needed only locally), and an FK would break the data import. The link is provided by the `(source, external_id)` pair.

**Indexes:** at ~150 rows every query is a full scan in the buffer pool anyway, so indexes for the filters from §13 #4 give nothing. Only these remain: the upsert key, `(city_slug, district_slug)` for the district list in `/api/meta`, and sorting by date. At 100k listings the indexes `(city_slug, price_pln)` and `(city_slug, area_m2)` are added.

### 3.4 Data provenance (W1)

Superseded for the details page by R19 (14.1): the details response carries no provenance. The text below stays as background for the dossier (16.1).

**Mechanism: provenance is a constant assigned to the field, not a column.** In this scope no field has two possible sources:
- fields from otodom → `listing`,
- `price_per_m2` and the “real price” → `computed`,
- facts from `listing_facts` → `description`,
- `NULL` in any field → `missing`.

The mapping is done by a single function `Provenance.For(fieldName, value)` in the Api, and the details response wraps each field in `{ "value": ..., "provenance": ... }` (6.2). Rejected alternative: the `*_source` columns from UC15. They make sense only when the same field can come from the advertisement or from the description, and here each such column would have a constant value.

Garage and parking are **two separate fields**, not merged: `hasGarage` (from the advertisement) and the `parking` fact (from the description, with a quote). Analogously `hasBasement` and `storage`.

### 3.5 `search_text` and text search

- **Construction (Ingest):** `TextFolding.Fold(title + " " + description_text + " " + district_name + " " + street + " " + cityName)`.
- **`TextFolding.Fold(s)`:**
  1. Unicode NFKD normalization,
  2. removal of characters of the `NonSpacingMark` category,
  3. replacement `ł→l`, `Ł→L` (they have no decomposition),
  4. `ToLowerInvariant`,
  5. replacement of every run of characters that are neither letters nor digits with a single space,
  6. `Trim`.

  The same function serves queries and the fallback; its steps 1–3 are also reused by the anchor normalization (5.1).
- **Query:** `text` (the text from the search field, 6.7) → `Fold` → split into tokens ≥ 2 characters (max. 5 tokens) → for each token `EF.Functions.Like(l.SearchText, "%" + token + "%", "\\")`, combined with AND. After `Fold` the token contains only `[a-z0-9]`, so there is no need to escape `%`/`_`.
- **No FULLTEXT:** at ~150 rows `LIKE` is instantaneous. It also avoids the lack of a Polish stemmer, `innodb_ft_min_token_size` and English stopwords. The substring “wrzeszcz” matches “Wrzeszczu”. At 100k listings an ngram parser or a search engine would be needed.

Format: a JSON array of strings, sorted alphabetically, without duplicates. A flag denotes a **transformation or an anomaly** that is not visible from the column value alone.

| `unknown_value:<column>` | enum value outside 3.3, e.g. `unknown_value:ownership` | details |

## 4. Normalization

### 4.1 Fetching (the `scrape` command)

- **Discovery:** `https://www.otodom.pl/pl/wyniki/sprzedaz/mieszkanie/pomorskie/{city}/{city}/{city}?by=LATEST&direction=DESC&market={PRIMARY|SECONDARY}&limit=36&page={n}`, where `city` ∈ {`gdansk`, `gdynia`, `sopot`}. The `market` parameter was verified: otodom redirects to `/mieszkanie,rynek-pierwotny/...`, and `HttpClient` follows the redirect.
  - List elements: `props.pageProps.data.searchAds.items[]`. We take only `estate == "FLAT"` and `hidePrice == false`, deduplication by `id` (promoted listings repeat across pages).
  - Quotas (constants in code, not in configuration): Gdańsk 55 primary + 55 secondary, Gdynia 30 + 30, Sopot 15 + 15. About 200 listings in total, ~150 after rejections.
- **Listing:** `https://www.otodom.pl/pl/oferta/{slug}`, regex `<script id="__NEXT_DATA__" type="application/json"[^>]*>(.*?)</script>` (Singleline; otodom adds `crossorigin="anonymous"` to the tag), `JsonDocument`, node `props.pageProps.ad`.
- **Transport:** one `HttpClient` with a browser User-Agent header and `AutomaticDecompression = All`. Delay of 1.5–3 s with random jitter, sequential.
  - 429/5xx: 3 retries after 5, 15 and 45 s.
  - 403 or no `__NEXT_DATA__` on the results page: the run ends with an error. The block page goes neither to the LLM nor to the database.
  - Listing page without `__NEXT_DATA__` or without the `props.pageProps.ad` node: `LogWarning("No ad node {Slug}")`, the listing is skipped and not saved (`ad_json` is `NOT NULL`).
  - At the end `scrape` prints: the number of requests, retries, skipped listings and saved listings per city × market. These counters are not in the database, so they do not go into `report`.
- **Privacy:** before saving, remove the keys `owner`, `agency`, `contactDetails`, `userAdverts` from `ad` (they contain phone numbers and names). Saved to `raw_listings` (upsert by `source, external_id`) and to the file `data/raw/otodom/{externalId}.json` (the source of fixtures).

### 4.2 Rules table (the `normalize` command, reads `raw_listings`, upserts into `listings`)

All paths are relative to `ad`. Numbers from otodom are sometimes a JSON number and sometimes a string (`target.Price` = `799000`, `target.Area` = `"41.86"`, `target.Rent` = `0` or `700`), so the parser `JsonNumber.ReadDecimal(JsonElement)` accepts both variants (`CultureInfo.InvariantCulture`). Array fields (`Rooms_num`, `Floor_no`, etc.) are arrays with a single string; we take `[0]`.

| JSON path | Column | Rule | Missing / invalid value |

**`HtmlText.ToPlain(html)`:**
1. `<br\s*/?>`, `</p>`, `</div>`, `</h[1-6]>`, `</li>` → `\n`;
2. `<li[^>]*>` → `\n- `;
3. remove the remaining tags `<[^>]+>`;
4. `WebUtility.HtmlDecode`;
5. U+00A0, U+202F, U+2007 → space;
6. in each line collapse spaces and trim;
7. 3+ consecutive `\n` → `\n\n`;
8. trim the whole;
9. **mask contact data typed into the description** (the privacy rule from 4.1 covers only JSON keys, but sellers also write phone numbers and e-mails into the text):
   - e-mail `[\w.+-]+@[\w-]+(\.[\w-]+)+` → `[e-mail ukryty]`;
   - phone `(?:\+48[\s-]?)?\b\d{3}[\s-]?\d{3}[\s-]?\d{3}\b` and `\b\d{2}[\s-]?\d{3}[\s-]?\d{2}[\s-]?\d{2}\b` → `[telefon ukryty]`.

   Masking happens before `search_text`, the LLM and the anchor, so the public demo and OpenAI never see the numbers, and quotes are still matched against the same (masked) text. Prices do not match the phone patterns: they have at most 7 digits (“1 250 000”).

**Upsert:** by `(source, external_id)`. If `description_text` has changed, set `facts_status = 'pending'` and delete the `listing_facts` rows of this listing. The status in `raw_listings.normalize_status` is saved together with the listing.

**Pitfall (EF Core + `EnableRetryOnFailure`):** with a retrying strategy EF Core throws `InvalidOperationException` on a manually opened transaction (`BeginTransaction`). Rule for all code: the changes of one operation are saved by **a single `SaveChangesAsync()`** on tracked entities (facts are deleted via `db.ListingFacts.RemoveRange(...)`, not via `ExecuteDelete`). If a transaction with several `SaveChanges` is really needed, then only inside `db.Database.CreateExecutionStrategy().ExecuteAsync(...)`.

### 4.3 Hard fields contract

A record goes into `listings` only if it has: `id`, `url`, `title`, flat/sale type, an explicit price > 0, area > 0, number of rooms, market, a city in scope and coordinates. A rejected record:
- stays in `raw_listings` with `normalize_status = 'rejected'` and `reject_reason` (codes from the 4.2 table: `missing_id`, `missing_url`, `missing_title`, `not_flat_sale`, `hidden_price`, `missing_price`, `missing_area`, `missing_rooms`, `missing_market`, `city_out_of_scope`, `missing_coordinates`),
- produces the log `LogWarning("Rejected {ExternalId}: {Reason}")`.

Soft fields never reject a record.

### 4.4 Report (the `report` command, also at the end of `all`)

Printed to stdout and saved to `docs/ingest-report.md`, overwritten on every run and committed, because the numbers for the 1-pager come from it.

1. **Fetched:** number of `raw_listings` rows per city × market, computed in C# from `ad_json` (`target.City`, `target.MarketType`), with an `unknown` bucket for records where either is missing (`raw_listings` has no city or market columns). The request counters are printed by `scrape` (4.1).
2. **Rejected:** number per `reject_reason`.
3. **Fill-rate** of every nullable column of `listings`, per city and in total (`n`, `%`). Covers assumption #1 from [product-scope.md](product-scope.md) §10.
4. **Flags:** number per flag.
5. **Rent (czynsz, maintenance fee):** share of `rent_zero_as_missing` per market (assumption #3).
6. **Cross table** `finish_condition` × `market` (the “nice” failure mode, [product-scope.md](product-scope.md) §11).
7. **Districts:** number of unique ones per city and a list of districts with 1 listing for manual review (assumption #2). Without a flag, because we have no reference list of administrative districts.
8. **Median `price_per_m2`** and `n` per city (assumption #5).
9. **Mini-W2:**
   - share of listings that passed the keyword prefilter (assumption #4),
   - number of calls, errors (`failed`) and `skipped`,
   - `accepted` / `rejected` facts per `fact_key`, rejections per `reject_reason`,
   - **share of rejected facts** = `rejected / (accepted + rejected)`.
10. **Duplicate candidates** (assumption #6): pairs of listings in the same `district_slug` with `rooms` equal, `area_m2` within ±0.5 m², `floor` equal (or both `NULL`) and `price_pln` within ±3 %; printed as the number of pairs, the share of listings in at least one pair and up to 10 pairs (`external_id`, `advertiser_type`) for manual review. Computed in memory (≤ 150 rows, O(n²) is trivial); nothing is flagged or grouped.
11. **Primary market in the “cheap” ranking** (assumption #7): share of `market = primary` among all listings vs among the 20 listings with the lowest `price_per_m2 / city median`, so the 1-pager can state whether “cheap” pushes developers down.

## 5. LLM enrichment at import (mini-W2, the `enrich` command)

**Prefilter (no LLM):** if `Fold(description_text)` contains none of the stems `postoj`, `garaz`, `parking`, `hala`, `komork`, `piwnic`, `schowek`, set `facts_status = 'skipped'`. This saves calls and gives the model no opportunity to make things up.

**Input:**
- system prompt from `prompts/listing-facts.v1.md`,
- user message = `description_text`. A description longer than 12 000 characters goes to the LLM truncated, with a log entry.

**Output (structured outputs: `response_format` of type `json_schema`, name `listing_facts`, `strict: true`):**

```json
{
  "type": "object", "additionalProperties": false, "required": ["parking", "storage"],
  "properties": {
    "parking": { "$ref": "#/$defs/fact" },
    "storage": { "$ref": "#/$defs/fact" }
  },
  "$defs": { "fact": {
    "type": "object", "additionalProperties": false, "required": ["status", "amountPln", "quote"],
    "properties": {
      "status":    { "type": "string", "enum": ["included", "extra_cost", "not_available", "not_mentioned"] },
      "amountPln": { "type": ["integer", "null"] },
      "quote":     { "type": ["string", "null"] }
    } } }
}
```

Strict mode rules (OpenAI documentation, checked 2026-11-04):
- every field must be in `required`, every object has `additionalProperties: false`;
- an optional field is a union of the type with `null`;
- `$defs`/`$ref` are supported, the root must be an object without `anyOf`;
- limit: 1 000 enum values in the whole schema.

`not_mentioned` exists only in the model's response: it gives the model an explicit “there is none” option and does not go into the database (no row = “no data”). Amount ranges and quote length are checked by code (5.1), not by the schema: `maxLength` is not supported, and domain rules have one place.

**Prompt (`prompts/listing-facts.v1.md`), substantive content:**
- `storage` = storage unit, cellar, storage closet, utility room;
- `included` = included in the flat price;
- `extra_cost` = extra charge, available for additional purchase, possibility of purchase;
- `not_available` = explicitly “none”;
- `quote` = a **verbatim, contiguous** fragment of the description ≤ 200 characters, copied character for character, without ellipses;
- `amountPln` only when the amount is the price of that item, in zloty, as an integer (“25 tys.” → 25000);
- example from the data: “komórka w cenie 60 000 zł” (storage unit for 60 000 zł) is `extra_cost` with an amount of 60000, and not `included`. This is the argument for “why not regex”.

### 5.1 Anchor validation (`AnchorValidator` in Core, deterministic, tested)

For each fact with `status != not_mentioned`, in this order:

1. `quote` empty or NULL → `rejected` / `missing_quote`.
2. `AnchorText.Normalize(quote)` must be a substring of `AnchorText.Normalize(description_text)`, otherwise `rejected` / `quote_not_found`.
3. `status == included` → `amount_pln = NULL` (the amount is ignored).
4. `status == extra_cost` and `amountPln != null`:
   - the amount must be equal to one of the numbers extracted from the normalized quote, otherwise `rejected` / `amount_not_in_quote`;
   - range: parking 5 000–300 000, storage 1 000–100 000, otherwise `rejected` / `amount_out_of_range`.
5. `status == extra_cost` without an amount → `accepted` with `amount_pln = NULL` (“extra charge, amount unknown”).
6. In the remaining cases → `accepted`.

**`AnchorText.Normalize(s)`:**
1. `WebUtility.HtmlDecode`;
2. NFKC;
3. U+00A0, U+202F, U+2007, U+2009, `\t`, `\r`, `\n` → space;
4. typography: `‘ ’ ‚ ‛` → `'`, `“ ” „ ‟ «  »` → `"`, `– — ‒ −` → `-`, `…` → `...`;
5. `TextFolding.Fold`-style diacritic removal (steps 1–3 from 3.5), but **without** replacing punctuation with spaces;
6. `ToLowerInvariant`;
7. collapse `\s+` to a single space and trim;
8. remove spaces between digits: regex `(?<=\d) (?=\d)` → `""` (so “60 000” = “60000”);
9. remove trailing `.,;:!` characters from the **quote** (not from the description).

**Numbers in the quote:** regex `(\d+(?:[.,]\d+)?)\s*(tys\.?|tys|k|mln)?` on the normalized quote. Multiplier: `tys`/`k` ×1 000, `mln` ×1 000 000, decimal comma = dot. The amount matches if `(long)Math.Round(number × multiplier)` == `amountPln`.

### 5.2 Errors, retry, parallelism

- Client: `new ChatClient(LLM_MODEL, new ApiKeyCredential(OPENAI_API_KEY), new OpenAIClientOptions { NetworkTimeout = TimeSpan.FromSeconds(60), RetryPolicy = new ClientRetryPolicy(maxRetries: 3) })`. The default SDK retry policy (`System.ClientModel`) retries 408/429/5xx and network errors with exponential backoff. Parallelism: `SemaphoreSlim(4)`.
- `ReasoningEffortLevel = new ChatReasoningEffortLevel(LLM_INGEST_REASONING_EFFORT)` (default `low`), `MaxOutputTokenCount = 2048`.
- Result per listing:
  - success and validation → upsert of 0–2 `listing_facts` rows (`accepted` or `rejected`), `facts_status = 'done'`;
  - after retries are exhausted (`ClientResultException`), on `Refusal != null`, `FinishReason` = `Length` or `ContentFilter`, or on a deserialization error → `facts_status = 'failed'`, `LogError` with `externalId` and the kind of error, the import continues. The listing then shows “no data”.
- A repeated `enrich` processes only `facts_status IN ('pending','failed')`.
- Cost with `gpt-6.1-terra` ($1 input / $5 output per 1M tokens): ~100 calls × ~2.5k input tokens and ~0.5k output tokens, i.e. ~$0.50 **[estimate]**.

### 5.3 Real price (W5)

Computed in the Api when reading details, not stored in the database:
- `extras` = accepted `parking`/`storage` facts with `status = extra_cost` and `amount_pln != NULL`;
- `realPrice.totalPln = price_pln + Σ extras.amount_pln`, provenance `computed`; the details response contains only the `realPrice` object (6.2), without a separate field in `fields`;
- the field is NULL when `extras` is empty.

Displayed **only in details**, under the price: “799 000 zł + parking space 60 000 zł (from the description) = 859 000 zł” and an expandable quote. When a listing has `extra_cost` without an amount, we show instead “Parking space at extra charge, amount unknown (from the description)”.

## 6. API contract

Common rules:
- JSON in camelCase;
- errors as `ProblemDetails` (`AddProblemDetails()` + `UseExceptionHandler()` + `UseStatusCodePages()`, the last one gives the body-less 400 of a failed parameter binding a ProblemDetails body); validation errors as `400` with `errors: { field: [message] }`;
- unknown `/api/*` path → `404` ProblemDetails (a separate `app.Map("/api/{**rest}", ...)` before the SPA fallback);
- all endpoints are in `Flatplanner.Api/Endpoints/*.cs` as Minimal API;
- **one serialization rule** (follows the Microsoft REST guidelines: do not send fields with a `null` value):
  - fields whose value is `null` are **omitted**: `builder.Services.ConfigureHttpJsonOptions(o => o.SerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull)`;
  - arrays are **always present** (empty = `[]`), booleans are **always present**;
  - there is no exception: a missing value in details is an omitted field, which the UI shows as “brak danych” (6.2, 14.1);
  - TypeScript types in `web/src/api.ts` mark every omittable field as optional (`why?: string`);
  - the options live in one static `ApiJson.Options` used both by `ConfigureHttpJsonOptions` and by `ApiSerializationTests` (section 12), which serialize sample DTOs and assert: no `:null` in the list response, `null` kept inside `remove`. `ConfigureHttpJsonOptions` verified in #1 for endpoints that return a DTO (`/api/meta` omits `dataAsOf` when it is `null`); `Results.Json` is given `ApiJson.Options` explicitly. **[TO BE VERIFIED]** for `TypedResults` in .NET 9 (aspnetcore issue #45872); the smoke test (11.5, step 7) checks the real HTTP response;
- **compression:** after the first deploy check `curl -sI -H 'Accept-Encoding: br, gzip' $URL/api/listings`. If the response has no `content-encoding`, add `builder.Services.AddResponseCompression(o => o.EnableForHttps = true)` and `app.UseResponseCompression()` before `UseStaticFiles` (Kestrel does not compress on its own; behind the proxy the request scheme is `https` after `UseForwardedHeaders`). BREACH needs a secret in the response next to reflected input; this API has no auth, cookies or CSRF tokens, so the risk is negligible. Compression is the only change with a real effect on transfer: JSON shrinks by ~70–85%, and the SPA bundle gains the most.

### 6.1 `GET /api/listings`

**Query parameters = names of the `SearchIntent` properties** (7.1) + `sort` + `page`. The same set of parameters forms the frontend URL (section 9).

| Parameter | Type | Validation / normalization (`SearchIntentNormalizer`, 7.3) |
|---|---|---|
| `cities` (repeatable) | string | slug from `/api/meta`; an unknown one is removed with a warning |
| `districts` (repeatable) | string `"{citySlug}:{districtSlug}"` | must exist in the data |
| `priceMin`, `priceMax` | int (PLN) | 10 000–20 000 000; min > max → swap |
| `areaMin`, `areaMax`, `areaApprox` | decimal with a **dot** | 10–300; the frontend replaces the comma with a dot before sending |
| `roomsMin`, `roomsMax` | int | 1–10 |
| `floorMin`, `floorMax` | int | −1–40 |
| `market` | string | `primary`/`secondary` |
| `advertiserType` | string | `agency`/`private` |
| `requireLift`, `requireBalcony` | bool | only `true` filters |
| `text` | string | ≤ 100 characters |
| `preferences` (repeatable) | string | `cheap`, `good_condition` |
| `requestedCityOutOfScope` | string | must match `^\p{L}[\p{L} \-]{1,39}$`, otherwise removed (7.3) |
| `outOfScope` (repeatable) | string | `rent`, `house`, `metro` |
| `sort` | string | 3.3; default `relevance` when `preferences` is non-empty, otherwise `newest` |
| `page` | int ≥ 1 | default 1; > `totalPages` → last page (UC1) |

A type error (e.g. `priceMin=abc`) → `400`. A semantically wrong value (unknown slug, number outside the range) is removed, and the reason goes to `interpretation.warnings`. One normalization path serves the form, the LLM and the fallback.

**Pagination: offset, `pageSize = 20` (a constant, not a parameter).** With ~150 rows the cost of `OFFSET` is zero. Offset gives numbered pages and a stable URL `?page=3`, which UC1 requires. Keyset rejected: it complicates sorting by the computed `relevance` and does not allow a jump to page N.

**Logic:**
1. `scopeBlocked = outOfScope ∩ {rent, house} ≠ ∅` → `items = []`, `total = 0`, `blockers` omitted. Results are not shown, the notices and chips remain (7.6).
2. SQL filters (7.4) → `total`.
3. Sorting:
   - `relevance` → rows satisfying the filters (≤ 150) are loaded into memory, ranking 7.5, then `Skip/Take`;
   - other sorts → `ORDER BY` in SQL, with `id DESC` as the last criterion.
4. `total == 0` and no `scopeBlocked` → `blockers` (6.4).

The list response does **not** echo the intent. The URL is the single source of truth (section 9), and the frontend never reads an echo; the normalized intent is returned only by `interpret` (6.3), where it is the actual result. What the normalizer changed is visible in the chips and in `interpretation.warnings`.

- the median of the city is not a separate field: it is already in `summary`, in each card's `why` and in the `median_fallback` notice (7.4, 7.6).

### 6.3 `POST /api/search/interpret`

**Name:** it returns an interpretation, not results. Results are always provided by `GET /api/listings` with the intent in the URL. Rationale in section 14, R1.

Request: `{ "message": "chcę ładne, tanie mieszkanie, 40 m w Gdańsku" }` (I want a nice, cheap flat, 40 m in Gdańsk).

Response `200`:

- `intent` follows the serialization rule: null fields are omitted, arrays and booleans are present. The frontend turns it into URL parameters with `intentToSearchParams` (section 9).
- `fallbackReason` ∈ `timeout | llm_error | schema_mismatch | refusal | disabled`; omitted when `usedFallback = false`.
- `promptVersion` is omitted on fallback.
- `intent` is already after `SearchIntentNormalizer`, and `warnings` (shape from 6.1) are the messages from this normalization, e.g. an omitted out-of-range amount. | `429` | rate limiter (section 8) | ProblemDetails `title: "Too many requests"`, header `Retry-After` |

### 6.4 “What is blocking” (UC12): part of the list response, not a separate endpoint

When `total == 0` and `scopeBlocked == false`:
- for each active chip with a key in {`cities`, `districts`, `price`, `area`, `rooms`, `floor`, `market`, `advertiserType`, `requireLift`, `requireBalcony`, `text`} we compute `Count(RemoveChip(intent, key))`, max. 11 COUNT queries;
- `blockers` = entries with `count > 0`, descending by `count`;
- `preferences:*` and `outOfScope:*` chips do not filter, so they are not blockers;
- field semantics: `blockers` **omitted** = not computed (`total > 0` or `scopeBlocked`); `blockers: []` = computed, and no single removal helps.

```json
"blockers": [
  { "key": "price", "label": "no price limit (up to 300 000 zł)", "count": 3, "remove": { "priceMin": null, "priceMax": null } },
  { "key": "rooms", "label": "without the condition: 3 rooms", "count": 2, "remove": { "roomsMin": null, "roomsMax": null } }
]
```

A separate endpoint rejected: it would require a second request on every zero result. The “what is blocking” logic belongs to the same intent as the list.

### 6.7 Keyword search (cut from the MVP)

Parsing the search field into filters (e.g. „Gdańsk Morena kawalerka” → city, rooms, text) was designed and cut, because it is the cheapest feature to drop without hurting either scenario. In the MVP the search field sets `text=` (`LIKE` on `search_text`, 3.5) and filters are set in the panel. Consequence: an out-of-scope city typed into the search field (e.g. „Kraków”) gives 0 results with “what blocks”; the explicit out-of-scope handling (UC13) works in the chat. With more time: a `KeywordQueryParser` on top of the same `KeywordRules` as the chat fallback (7.7), returning an intent once, so that removing a chip is not undone by re-parsing.

### 7.1 C# record (`Flatplanner.Core/Search/SearchIntent.cs`)

**`SearchMeta` (Core, `Flatplanner.Core/Search/SearchMeta.cs`):** the dictionary every component of the search needs (normalizer, both parsers, the schema builder, the prompt), loaded from the database by `SearchMetaLoader.LoadAsync(FlatplannerDbContext db, CancellationToken ct)`. It lives in Core so that Ingest (`eval-intents`) can load it from the local database without referencing Api.


`SearchMetaLoader` runs one `SELECT DISTINCT city_slug, district_slug, district_name FROM listings` per call (no cache, ~1 ms). `MetaService` in Api builds the `/api/meta` response from it (6.5) by adding labels and counts. Wherever this document writes `meta` as an argument, it means `SearchMeta`.

**`SearchIntent` is only a data structure with filters, not a processing step.** There are three independent ways to search. Each produces the same type, but only the chat uses AI:

| Input | What the user types | How `SearchIntent` is created | AI |
|---|---|---|---|
| **Filters** | form fields | 1:1 from URL parameters: `GET /api/listings` binds them via `[AsParameters] ListingsQuery` (= `SearchIntent` fields + `Sort` + `Page`; booleans as `bool?` mapped with `?? false`, because a non-nullable parameter without a value can be treated as required and give 400) | no |
| **Search** | „Morena” | the text goes 1:1 to `text` (`LIKE`, 3.5); no parsing (6.7) | no |
| **Chat** | „chcę ładne, tanie mieszkanie, 40 m w Gdańsku” (I want a nice, cheap flat, 40 m in Gdańsk) | LLM via `POST /api/search/interpret` (6.3); on failure `IntentFallbackParser` | yes |

Results are always returned by `GET /api/listings`. Every input ends up at `SearchIntentNormalizer.Normalize(intent, meta)` (7.3); for filters, inside `GET /api/listings`. The frontend has a `SearchIntent` type in `web/src/api.ts` with identical field names.

**URL ↔ `SearchIntent`:** parameter name = field name in camelCase. Arrays are repeated parameters, `null`/`false`/`[]` are omitted from the URL. Example: `/?cities=gdansk&areaApprox=40&preferences=cheap&preferences=good_condition&sort=relevance&page=2`. Functions `intentFromSearchParams` and `intentToSearchParams` in `web/src/intent.ts`.

### 7.3 `SearchIntentNormalizer.Normalize` (code decides, the model only translates)

Steps in this order. A message goes to `warnings` **only when the normalizer removes, clips or replaces a value the user (or the model) gave**: an unknown slug, a value outside its range, a district outside the selected cities, an invalid `requestedCityOutOfScope`, a dropped `areaApprox`. Silent housekeeping produces no warning: reordering cities, filling `cities` from districts, the default city for an out-of-scope city (that one is already explained by the `city_out_of_scope` notice), swapping min > max.

1. `cities`: only slugs from `meta`, without duplicates, in the order gdansk, gdynia, sopot.
2. `districts`: only existing keys. When `cities` is non-empty, remove districts outside those cities. When `cities` is empty but districts are present, set `cities` = the cities of those districts.
3. `requestedCityOutOfScope`: trim; must match `^\p{L}[\p{L} \-]{1,39}$` (just a city name, no digits or special characters), otherwise `null`. This value from the URL ends up in a UI message, so the validation blocks links with arbitrary text on the demo domain. If set and `cities` is empty → `cities = [meta.DefaultCitySlug]` (`gdansk`, the largest part of the data).
4. Ranges: min > max → swap. Values outside the ranges from 6.1 → `null`.
5. `areaApprox` together with `areaMin`/`areaMax` → the explicit range wins, `areaApprox = null`.
6. `market`, `advertiserType` outside the enum → `null`.
7. `preferences`, `outOfScope`: filter to allowed values, without duplicates, canonical order from 3.3.
8. `text`: trim, max. 100 characters, empty → `null`.

### 7.4 Tolerances and definitions (constants in `SearchDefinitions`)

| Concept | Rule in code |
|---|---|
| „40 m” (`areaApprox = a`) | `areaMin = floor(a × 0.88)`, `areaMax = ceil(a × 1.12)` → 40 gives **35–45 m²**. Bounds inclusive. |
| SQL filters | `city_slug IN cities`; districts as an OR of pairs `(city_slug = c AND district_slug = d)`; `price_pln`, `area_m2`, `rooms`, `floor` via `>=`/`<=` (listings with `floor IS NULL` drop out when the floor filter is used); `market =`; `advertiser_type =`; `requireLift` → `has_lift = 1`; `requireBalcony` → `has_balcony = 1`; `text` → 3.5 |
| “cheap” (`cheap`) | **Soft preference, not a filter.** Reference group = **all** listings from the listing's city (not only the filtered ones). When the city has `n < 10`, the group is the whole Tricity (Trójmiasto), with the notice `median_fallback` (“Too few listings from Sopot (n=8), I calculate ‘cheap’ relative to the whole Tricity (n=150).”). `cheapScore = 1 − percentRank`, where `percentRank = (number in the group with a lower price/m² + 0.5 × number with an equal one) / n`. **Listings with the `price_outlier` flag do not enter the reference group** (neither the median nor `n`) and get `cheapScore = 0`. The SQL query for the reference group filters by `price_per_m2 BETWEEN SearchDefinitions.PricePerM2Min AND SearchDefinitions.PricePerM2Max` (7 000 and 40 000, the same constants that set the flag in 4.2), **not** by `quality_flags`: that column is a `string[]` mapped through `HasConversion`, and `QualityFlags.Contains("price_outlier")` cannot be translated to SQL (runtime exception). On the card, `priceOutlier` is still read from the flag in memory. Such a listing shows, and in “Why here”, instead of the comparison with the median: “unusual price/m², check the description”. Without this, a listing with a wrong price (e.g. 450 zł instead of 450 000 zł, sale of a share) would win the “cheap” ranking in scenario B. |
| “Cheap” description in “Why here” | `delta = price_per_m2 / median − 1`. `delta ≤ −5%` → “X% cheaper per m² than the {city} median”; `|delta| < 5%` → “price/m² close to the {city} median”; `delta ≥ 5%` → “X% more expensive per m² than the {city} median”. When the base is the whole Tricity, we substitute “Tricity” in place of the city name. |
| “nice” (`good_condition`) | `finish_condition`: `ready_to_use` → 1.0; `NULL` → 0.5 (no data, neutral); `to_completion` → 0.0; `to_renovation` → 0.0. On the primary market this works like “secondary market” (failure mode from [product-scope.md](product-scope.md) §11, described in the README and the 1-pager). |
| Median | `price_per_m2` from the reference group (without `price_outlier`): for an even `n` the average of the two middle values, rounded to 100 zł. |

### 7.5 Ranking (`sort = relevance`)

- `score = Σ(w_k × s_k) / Σ(w_k)` for the preferences present in the intent. Fixed weights: `cheap = 0.7`, `good_condition = 0.3`. Listed in the README.
- Ties: `created_at_source DESC`, then `id DESC`. Without preferences `relevance` gives the `newest` order.
- **“Why here”** (`why`, only when `preferences` is non-empty) is a single line of elements separated by ` · `:
  1. `{area_m2} m²` (decimal comma),
  2. `{district_name ?? cityName}`,
  3. for `cheap`: the description from 7.4,
  4. for `good_condition`: “condition: {label} (from the advertisement)” or “condition: no data”.

### 7.6 Chips and notices (`InterpretationBuilder` in Api)

| `floor` | “ground floor”, “floor 0–2” | `floorMin`, `floorMax` |
| `market` | “secondary market” | `market` |

| `requireLift` | “with a lift” | `requireLift` |

### 7.7 LLM call and fallback

**Path in `ChatInterpreter.InterpretAsync(message)` (Api):**
1. `CHAT_MODE=fallback` → fallback, `disabled`.
2. `IntentInterpreter.InterpretWithLlmAsync(message, meta, ct)` (Core; the same core is used by `eval-intents`) calls `LlmJsonClient.CompleteJsonAsync<SearchIntent>(...)`:
   - `system` = `prompts/search-intent.v1.md` with `{{CITY_LIST}}` and `{{DISTRICT_LIST}}` substituted (lines `gdansk:letnica — Letnica (Gdańsk)` built from `SearchMeta`);
   - `user` = the message;
   - `ChatCompletionOptions { ResponseFormat = <7.2>, ReasoningEffortLevel = new ChatReasoningEffortLevel(LLM_CHAT_REASONING_EFFORT), MaxOutputTokenCount = 1024 }`; the default chat effort is `none` (lowest latency; intent extraction does not require reasoning);
   - `CancellationTokenSource(TimeSpan.FromSeconds(CHAT_TIMEOUT_SECONDS))` passed to `CompleteChatAsync(messages, options, cts.Token)`;
   - chat client: `new OpenAIClientOptions { NetworkTimeout = TimeSpan.FromSeconds(CHAT_TIMEOUT_SECONDS), RetryPolicy = new ClientRetryPolicy(maxRetries: 1) }`; one retry fits within the total 5 s budget, because the CTS cuts it off.
3. Mapping errors to fallback:

   | Error | `fallbackReason` |
   |---|---|
   | `OperationCanceledException` | `timeout` |
   | `ClientResultException` (any `Status`, including 429 with the code `project_spend_limit_exceeded`, section 8), `HttpRequestException` | `llm_error` |
   | `completion.Refusal != null` or `FinishReason == ChatFinishReason.ContentFilter` | `refusal` |
   | `FinishReason == ChatFinishReason.Length` or `JsonException` during deserialization | `schema_mismatch` |

   Every fallback produces a `LogWarning` with the reason and the prompt version, without the message content.
4. Success **or** fallback → `SearchIntentNormalizer.Normalize`. Both paths return a normalized intent with its `warnings` (6.3).

**SDK call shape** (compiled with `OpenAI` 2.14.0 on net9.0; `using OpenAI; using OpenAI.Chat; using System.ClientModel; using System.ClientModel.Primitives;`):

```csharp
#pragma warning disable OPENAI001 // ReasoningEffortLevel is experimental in 2.14.0 (or NoWarn in the Core csproj)
var client = new ChatClient(options.LlmModel, new ApiKeyCredential(options.OpenAiApiKey),
    new OpenAIClientOptions { NetworkTimeout = timeout, RetryPolicy = new ClientRetryPolicy(maxRetries: retries) });

var completionOptions = new ChatCompletionOptions
{
    ResponseFormat = ChatResponseFormat.CreateJsonSchemaFormat(
        jsonSchemaFormatName: schemaName,                 // "search_intent" | "listing_facts"
        jsonSchema: BinaryData.FromString(schemaJson),
        jsonSchemaIsStrict: true),
    ReasoningEffortLevel = new ChatReasoningEffortLevel(effort),   // "none" | "low" | ...
    MaxOutputTokenCount = maxOutputTokens,
};

ChatCompletion completion = await client.CompleteChatAsync(
    [new SystemChatMessage(systemPrompt), new UserChatMessage(userText)], completionOptions, ct);

if (completion.Refusal is not null || completion.FinishReason == ChatFinishReason.ContentFilter) throw new LlmException(LlmFailure.Refusal);
if (completion.FinishReason == ChatFinishReason.Length) throw new LlmException(LlmFailure.Truncated);
var json = completion.Content.Count > 0 ? completion.Content[0].Text : throw new LlmException(LlmFailure.SchemaMismatch);
```

**Deserialization (a trap):** the default `System.Text.Json` is case-sensitive, so `"cities"` from the model's response would **not** land in the `Cities` property. The result would be an empty intent without any exception, with `usedFallback: false`, i.e. a list of all listings. `LlmJsonClient` deserializes exclusively with:

```csharp
static readonly JsonSerializerOptions LlmJson = new(JsonSerializerDefaults.Web)  // camelCase, case-insensitive
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow,                 // unknown field → JsonException → schema_mismatch
};
```

`LlmJsonClient` is the only place that knows the OpenAI SDK types. The rest of the code operates on `LlmException(LlmFailure)` with the values `Timeout | ApiError | Refusal | Truncated | SchemaMismatch`. We use Chat Completions, not the Responses API: the page of the model `gpt-6.1-terra` lists both endpoints, we do not need tools, and the Chat client is stable in the SDK.

**Prompt `prompts/search-intent.v1.md`, rules:**
- return only the schema fields;
- cities only from the list; „Trójmiasto/3miasto/w Trójmieście” → all three;
- a city outside the list → `requestedCityOutOfScope` in the nominative and `cities: []`;
- „ok. 40 m”/„40 m” → `areaApprox`; „40–80 m” → `areaMin`/`areaMax`;
- „tys.” ×1 000, „mln” ×1 000 000;
- „kawalerka” → `roomsMin = roomsMax = 1`; „2 pokoje” → 2/2;
- „parter” → `floorMin = floorMax = 0`; „max 2 piętro” → `floorMax = 2`;
- „tanie/tanio/okazja” → `cheap` (without `priceMax`, if no amount was given);
- „ładne/zadbane/po remoncie/do wprowadzenia” → `good_condition`;
- „bez pośredników/od właściciela” → `advertiserType = private`;
- „nowe/od dewelopera/rynek pierwotny” → `market = primary`;
- „z windą” → `requireLift`; „z balkonem” → `requireBalcony`;
- wynajem/najem → `outOfScope: rent`; dom/szeregowiec/bliźniak → `house`; metro → `metro`;
- do not invent filters that the user did not give;
- the message may be in English (e.g. „nice, cheap flat, 40m”); map it to the same fields;
- 4 few-shot examples, **different from the 10 test queries** (section 12), one of them in English.

**Versioning:**
- a prompt change = a new file `search-intent.v2.md` + a change of the constant `PromptVersions.SearchIntent`; the old file stays for comparison;
- the version goes into the log of every call and into the `promptVersion` field of the response;
- directory path: `PROMPTS_DIR`, by default `prompts` relative to `ContentRootPath` (in the container `/app/prompts`, in Ingest the repo directory).

**Fallback `IntentFallbackParser.Parse(message, meta)` (Core):**

The rules live in one table, `KeywordRules` (below), so a future keyword search (6.7) can reuse them. The rest of the text after the matches is **discarded**, because the whole sentence in `LIKE` would give 0 results.

**Districts** (dictionary from `meta`, names after `Fold`) are matched on a **separate copy of the message after plain `Fold`**, not on the punctuation-keeping variant (otherwise „Piecki-Migowo” would stay `piecki-migowo` and match neither `piecki migowo` nor `piecki`): the full district name as a substring → that district; otherwise a token equal to the first word of the name (≥ 4 characters) → all districts with that first word („wrzeszcz” → Wrzeszcz Górny and Wrzeszcz Dolny).

Input: `TextFolding.FoldKeepingNumberPunctuation(message)`, i.e. `Fold` from 3.5, in which the characters `.`, `,` and `-` **are kept** (otherwise „40-80 m2” would lose its range). NFKD turns `²` into `2`, so „m²” gives „m2”. Rules in order:

| Target | Pattern (on the text after folding) | Result |
|---|---|---|
| m² range | `(\d+(?:[.,]\d+)?)\s*(?:-|do)\s*(\d+(?:[.,]\d+)?)\s*(?:m2|m|mkw|metr\w*)\b` | `areaMin`, `areaMax` |
| single m² | `(\d+(?:[.,]\d+)?)\s*(?:m2|m|mkw|metr\w*)\b` (when there is no range) | `areaApprox` |
| max price | `(?:do|max|maks\w*|ponizej)\s*(\d+(?:[.,]\d+)?)\s*(tys|k|mln)\b` | `priceMax` × multiplier |
| min price | `(?:od|powyzej|min)\s*(\d+(?:[.,]\d+)?)\s*(tys|k|mln)\b` | `priceMin` × multiplier |
| max price in zloty | `(?:do|max|maks\w*|ponizej)\s*(\d{1,3}(?: \d{3})+|\d{4,})\s*(?:zl|pln)?\b` (e.g. „do 600 000 zł” (up to 600 000 zł), „do 600000” (up to 600000)); spaces are removed from the number | `priceMax` |
| min price in zloty | `(?:od|powyzej|min)\s*(\d{1,3}(?: \d{3})+|\d{4,})\s*(?:zl|pln)?\b` | `priceMin` |
| rooms range (checked first) | `\b(\d)\s*-\s*(\d)\s*pok\w*` (e.g. „2-3 pokoje”) | `roomsMin`, `roomsMax` |
| rooms | `\b(\d)\s*pok\w*`; `kawalerk\w*` → 1 | `roomsMin = roomsMax` |
| ground floor | `\bparter\w*` | `floorMin = floorMax = 0` |
| in-scope cities | `gdansk|gdanska|gdansku` → gdansk; `gdynia|gdyni|gdynii|gdynie` → gdynia; `sopot|sopotu|sopocie` → sopot; `trojmiasto|trojmiescie|trojmiasta|3miasto` → all | `cities` |
| districts | dictionary from `meta`, matching described above | `districts` |
| out-of-scope cities | Warszawa (`warszawa|warszawie|warszawy`), Kraków (`krakow|krakowie|krakowa`), Wrocław (`wroclaw|wroclawiu|wroclawia`), Poznań (`poznan|poznaniu|poznania`), Łódź (`lodz|lodzi`), Szczecin (`szczecin|szczecinie|szczecina`), Bydgoszcz (`bydgoszcz|bydgoszczy`), Lublin (`lublin|lublinie|lublina`), Katowice (`katowice|katowicach`), Białystok (`bialystok|bialymstoku|bialegostoku`) | `requestedCityOutOfScope` = the name in the nominative with Polish characters |
| out of scope (fallback only) | `wynaj\w*|najem|najmu` → rent; `\bdom\b|\bdomu\b|domek|szeregow\w*|blizniak\w*` → house; `\bmetr(o|a|em|ze)\b` → metro | `outOfScope` |
| preferences (fallback only) | `\btani\w*|\btanio\b|okazj\w*|\bcheap\b` → cheap; `\bladn\w*|zadban\w*|po remoncie|do zamieszkania|do wprowadzenia|\bnice\b` → good_condition. The two English words cover the scenario B sentence from the task, which an evaluator is likely to paste verbatim | `preferences` |

City patterns are matched with `\b` on both sides. The dictionaries are constants in `FallbackDictionaries`. „metro” is recognised before the „m” rule (floor area), because the m² regex requires a number before the unit.

The user sees above the results: “Simplified query understanding (AI temporarily unavailable): I recognise numbers, cities and a few keywords. Correct the filters below.” plus the usual chips and filters.

## 8. Protection of the public chatbox

Middleware order in `Program.cs`: `UseExceptionHandler` → `UseStatusCodePages` → `UseRateLimiter` → `UseDefaultFiles` → `UseStaticFiles` → endpoints → `MapFallbackToFile("index.html")`.

**Client IP:** behind the Railway proxy `RemoteIpAddress` is the proxy edge address, so the per-IP limiter would put everyone into one bucket. Verified on the deployed skeleton (§13 #2, 2026-11-05), from a home network and from a phone on LTE:

| Network | `X-Real-IP` | `X-Forwarded-For` | `RemoteIpAddress` |
|---|---|---|---|
| home (`curl -4 ifconfig.me` = `77.236.31.78`) | `77.236.31.78` | `[::ffff:100.64.0.3]:56572` | `152.233.43.34` |
| phone, LTE | `37.248.214.112` | `[::ffff:100.64.0.4]:54532` | `152.233.43.34` |

`X-Real-IP` carries the client address. `X-Forwarded-For` holds the internal proxy address (100.64.x.x, with a port) and `RemoteIpAddress` the platform edge, so neither identifies the client. Decision: the partition key and `/api/health.clientIp` are the `X-Real-IP` header, falling back to `RemoteIpAddress`. `UseForwardedHeaders` is not used. A request with a forged `X-Real-IP: 1.2.3.4` still returned the caller's real address, so the edge overwrites the header. Plan B: section 15, K5.

**Rate limiter** (`AddRateLimiter`, built into ASP.NET Core 9):

| Policy | Scope | Partition | Limit |
|---|---|---|---|
| `GlobalLimiter` | `/api/*` only: the partitioner returns `RateLimitPartition.GetNoLimiter` for other paths, so static files and the SPA are not counted | IP | FixedWindow 120 req / 1 min, `QueueLimit = 0` |
| `"chat"` (`.RequireRateLimiting("chat")` on `/api/search/interpret`) | chat | IP | FixedWindow 5 req / 1 min, `QueueLimit = 0` |

`RejectionStatusCode = 429`. `OnRejected` writes ProblemDetails and the `Retry-After` header from `MetadataName.RetryAfter`. Partition key: the client IP defined above, `"unknown"` when both are absent.

**Length limit:** `message` after trim 1–300 characters (`CHAT_MAX_LENGTH`, section 10). Longer → 400 without calling the model. The frontend has `maxLength=300` on the textarea.

**No application-level budget counter.** Cost is capped by the hard spend limit at the provider (below); the per-IP limiter caps how fast one client can spend it, and `CHAT_MODE=fallback` is the kill switch. A daily counter in the database was rejected: it would not prevent the outage (one client at 5 queries/min exhausts any shared daily limit within hours), it would only shorten it to midnight, at the cost of a table, a migration and a test. With `gpt-6.1-terra`, ~2.5k input tokens and ~0.3k output tokens per call (~$0.004) **[estimate]**, a $20 limit is ~5000 calls. In production the right tool is per-user quotas and budget alerts (1-pager, “with more time”).

**Spend limit at the provider:**
- a separate **project** in the OpenAI Platform (e.g. `flatplanner`) and an API key assigned only to it;
- Project settings → **Limits** → Spend → **Edit spend limit**: monthly limit $20, **Enforce a hard limit** enabled (“Spend limits” documentation, checked 2026-11-04);
- after the limit is exceeded the API returns `429` with the code `project_spend_limit_exceeded`, and the code treats this like any API error, i.e. switches to the fallback (7.7). Enforcement is not instantaneous, so spend may slightly exceed the limit;
- an additional ceiling: prepaid credits on the account (automatic top-up disabled); once they are exhausted the API also returns an error **[TO BE VERIFIED]** (the code `credit_balance_exhausted` confirmed only in a secondary source);
- the key goes in Railway environment variables, never in the repo.

This is a hard ceiling independent of the code.

**Environment flag** (cut 8 from the list in 14.4): `CHAT_MODE` = `llm` | `fallback`.
- `fallback` is the LLM kill switch: the chat works at no cost and without network, on the parser alone. Used on the skeleton and always when something is wrong with the key or with the protection.
- There is no “chat completely disabled” mode: `fallback` implements this cut, and a separate mode would require handling 503 and hiding the switch in the frontend with no real gain.

## 9. Frontend

**Views:**
- `/`: list. Layout from the top:
  1. **search bar with a mode switch** “Search | AI chat”: in search mode a single-line field for `text` (“np. Morena, Wrzeszcz, balkon”), in chat mode a textarea (“e.g. chcę ładne, tanie mieszkanie, 40 m w Gdańsku” (I want a nice, cheap flat, 40 m in Gdańsk)). This is exactly scenario B from the task description: “chat box instead of search input”. When `chatMode = fallback`, below the chat field there is a permanent note “simplified mode, no AI”;
  2. notices, chips;
  3. **filter panel**, always visible and independent of the bar;
  4. sorting, result count, cards, pagination, “what blocks” on 0 results.
- `/listings/:id`: details (since #7′b it redirects to `/?listing=:id`, R25).

Chat and search are part of the home page, not separate views, because their result is the same list. A separate view would duplicate the list.

**Three modes, the combining rule:**
- **search and chat start a new search:** their result **replaces** the entire intent in the URL;
- **filters narrow the current search:** they change only their own parameters and leave the rest (e.g. `text` from search or `preferences` from chat);
- **chips** show the state regardless of where it came from, and each of them can be removed.

Example: “Gdańsk Morena kawalerka” in search, then a price of up to 500 000 zł in the filters → URL `/?cities=gdansk&roomsMin=1&roomsMax=1&text=morena&priceMax=500000`.

**State in the URL:**
- parameters from 7.1 + `sort` + `page`. The only source of truth is `useSearchParams()` from react-router;
- the list component computes `intent = intentFromSearchParams(searchParams)` and calls `useQuery({ queryKey: ['listings', searchParams.toString()], queryFn: () => fetchListings(searchParams), placeholderData: keepPreviousData, retry: (count, err) => isServerOrNetworkError(err) && count < 1 })` (TanStack Query v5 object syntax). `keepPreviousData` keeps the previous list while the new one loads (no layout jump); 4xx errors, including 429, are not retried, while 5xx and network errors get one retry;
- **“Clear filters”** removes only the filter panel parameters (`cities`, `districts`, `priceMin/Max`, `areaMin/Max/Approx`, `roomsMin/Max`, `floorMin/Max`, `market`, `advertiserType`, `requireLift`, `requireBalcony`) and `page`. `text` and `preferences` stay, because they come from search and chat; they are removed with a chip;
- **sorting `relevance`** is visible in the select only when `intent.preferences` is non-empty; without preferences there is nothing to rank by (3.3);
- **filter form:** local state initialized from the URL; there is no “Apply” button: every change writes the URL (`page` removed) via `setSearchParams`, immediately for pills and checkboxes and after 500 ms without typing for the numeric fields. A URL change that the current form did not cause (back/forward, “Clear filters”) resets the form to the URL. Numeric fields replace `,` with `.` before saving. The form owns exactly the parameters listed under “Clear filters” above; it never touches `text`, `preferences`, `requestedCityOutOfScope` or `outOfScope`, with two exceptions applied on every write:
  - setting `areaMin` or `areaMax` **removes `areaApprox`** (otherwise the approximate area from the chat stays in the URL next to the explicit range, and the normalizer warns about it on every page and sort);
  - clearing `cities` **removes `requestedCityOutOfScope`** (otherwise the normalizer puts `gdansk` back, and the form shows “no city” next to results from Gdańsk);
- **errors of the chat** (shown under the field, the field keeps its text):
  - `429` → “Too many queries. Try again in {Retry-After} s.”;
  - `400` → the fixed Polish text from [ui-spec.md](ui-spec.md) §7.1 (`errors.message` from ProblemDetails is only logged in the browser console, it is not shown);
  - network error or 5xx → “Could not connect. Use the filters below.”;
- **sorting and pagination:** written to the URL immediately;
- **search:** no API call; “Search” writes `text=<value>` (trimmed, max 100 characters; empty value deletes `text`), removes `page` and keeps the other parameters, so it narrows the current result like a filter. The search field shows the current `text`; the `text` chip removes it. `interpretation.warnings` are shown above the chips;
- **chat:** `POST /api/search/interpret` → `navigate({ pathname: "/", search: intentToSearchParams(resp.intent).toString() }, { state: { fromChat: true, usedFallback: resp.usedFallback, fallbackReason: resp.fallbackReason, warnings: resp.warnings } })`. Chat **replaces** the entire intent, it does not combine it with the filters. The fallback banner and the “I understood:” prefix read `location.state`, which survives “back”;
- **chip / blocker / notice button:** remove from a copy of `searchParams` every `remove` element (`value == null` → `delete(param)`, otherwise remove that one value), remove `page`, `setSearchParams`. `location.state` is deliberately **not** carried over: after a manual change of the intent, the fallback banner and the “I understood:” prefix would no longer describe what is on the screen, so they disappear;
- **“back” from details:** plain browser history. The TanStack Query cache (`staleTime: 60_000`) shows the list immediately;
- **districts in the filter:** from `/api/meta`, narrowed to the selected cities, grouped by city, with counts.

**Details:**
- a table of fields with a provenance badge (labels from `/api/meta.enums.provenance`), “no data” instead of empty spots;
- a “Real price” block with a quote, “Approximate location”, “Data quality notes” (flags with labels), “Ask the seller about:”, a link to otodom, and the stale-data note built from `scrapedAt` (text in [ui-spec.md](ui-spec.md) §7.1) (not an API field, 6.2);
- the description as **text with light markup** (`description_markup`: bold, italic, paragraphs and bullet lists, turned into React elements by our own parser; falls back to `description_text`). HTML is never rendered, so there is no XSS;
- photos as `<img loading="lazy" referrerPolicy="no-referrer">`.

**Libraries:**
- `react-router` 8.5.1 (imports only from `react-router`; there is no `react-router-dom` package in v8): routing and `useSearchParams`/`location.state` for state in the URL and “back”; without it the History API would have to be handled manually;
- `@tanstack/react-query` 5.105.3: cache per URL (instant return), loading and error states and cancelling previous requests in one hook; a manual `useEffect` gives response races.

No component library and no design system: a single `web/src/styles.css`. DTO types written by hand in `web/src/api.ts` (~10 types). An OpenAPI generator is an additional build step with no gain at this number of types.

**Files:**
- `web/index.html` with `<meta name="robots" content="noindex">`: the demo republishes scraped listings and must not compete with the source in search engines;
- `main.tsx`, `App.tsx` (routes), `api.ts`, `intent.ts`, `styles.css` (tokens and styles, `docs/ui-spec.md` §2);
- `format.ts`: Polish labels of detail fields, quality flags and fact keys (`docs/ui-spec.md` §7.2), price and area formatting, plural forms, floor (“ground floor”, “11+”). The labels are frontend constants and not part of `/api/meta`, because they are interface text, not data;
- `pages/AskPage.tsx`, `pages/ListingsPage.tsx`, `pages/ListingDetailPage.tsx`;
- `components/SearchBar.tsx` (mode switch + search + chat), `Filters.tsx`, `Interpretation.tsx` (chips, notices, banner), `ListingCard.tsx`, `Pagination.tsx`, `Blockers.tsx`; the ask page (16.2, ui-spec 11.2): `AskResults.tsx`, `AskCard.tsx`, `AskProgress.tsx`, `NeedVerdict.tsx`, `RiskList.tsx`.

2. **`build`** (`mcr.microsoft.com/dotnet/sdk:9.0`): copies `global.json`, `Directory.Build.props`, the Core and Api `.csproj` files → `dotnet restore src/Flatplanner.Api` → `COPY src/` → `dotnet publish src/Flatplanner.Api -c Release -o /out --no-restore`.
3. **`runtime`** (`mcr.microsoft.com/dotnet/aspnet:9.0`):
   - `WORKDIR /app`;
   - copies `/out`, `/web/dist` → `./wwwroot`, `prompts/` → `./prompts` (the `prompts/` copy is added together with the first prompt file in #7);
   - `ENV ASPNETCORE_HTTP_PORTS=8080`, `EXPOSE 8080`;
   - `USER $APP_UID` (a non-root user, provided by the image);
   - `ENTRYPOINT ["dotnet", "Flatplanner.Api.dll"]`.

Ingest and Tests do not end up in the image.

### 11.3 Production: Railway (recommendation)

**Why Railway:**
- one project holds a container from the Dockerfile and MySQL (the official `mysql` image, i.e. full `JSON` and `FULLTEXT`);
- a private network between services, automatic HTTPS on the `*.up.railway.app` domain, a TCP proxy for the one-off data import;
- one platform means one account, one set of variables and one log panel.

**Terms (checked 2026-11-04, railway.com/pricing):**
- Hobby: $5/month with $5 of usage included; Free Trial: a one-time $5 for 30 days, no card, volume max. 500 MB;
- usage: ~$20/vCPU-month, ~$10/GB RAM-month, $0.15/GB of volume;
- estimate for the API (~0.25 GB) and MySQL (~0.5 GB): ~$7–8/month **[estimate]**.

Recommendation: **Hobby**, because the Trial may run out during the evaluation.

**Deploying the empty skeleton (§13 #2):**
1. Repo on GitHub (a private one is enough) → Railway: New Project → Deploy from GitHub repo. Railway detects the `Dockerfile`.
2. In the same project: + New → Database → MySQL.
3. Variables of the application service:
   - `ConnectionStrings__Default=Server=${{MySQL.MYSQLHOST}};Port=${{MySQL.MYSQLPORT}};Database=${{MySQL.MYSQLDATABASE}};User=${{MySQL.MYSQLUSER}};Password=${{MySQL.MYSQLPASSWORD}};CharSet=utf8mb4` (Railway reference variables);
   - `CHAT_MODE=fallback`, `DB_MIGRATE_ON_STARTUP=true` (the port comes from `ASPNETCORE_HTTP_PORTS=8080` in the Dockerfile, section 10).
4. Settings → Networking → Generate Domain (port 8080) → a public URL with HTTPS. Healthcheck path: `/api/health`.
5. Check: `GET /api/health` → `db: ok`; `/` shows the SPA (an empty list); `GET /api/listings` → `total: 0`.
6. Migrations: they are applied at container startup, because it is a single instance and there is no race. If a migration fails, the container does not come up, and the Railway log shows the exception.

The MySQL version from the Railway template is 8.4.13 (`SELECT VERSION();`, checked 2026-11-05). Pomelo with `ServerVersion 8.4` works with 8.x; for 9.x see K1 (section 15).

**HTTPS:** terminated by the Railway proxy. The application listens on HTTP on 8080, without `UseHttpsRedirection` (the redirect is done by the platform).

### 11.4 Data transfer (§13 #15)

All commands go through the MySQL client from the local `mysql` container, so there is no need to install `mysql` on the laptop. **`-T` is mandatory:** without it `docker compose exec` allocates a TTY, and then stderr warnings and `\r` characters may end up in the dump file, which makes the import on production fail on the first line. The password is passed via the `MYSQL_PWD` variable, because without a TTY `-p` cannot ask for it interactively.

```bash
docker compose exec -T -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql mysqldump -uroot --no-create-info --complete-insert --single-transaction --skip-add-locks --set-gtid-purged=OFF --default-character-set=utf8mb4 flatplanner listings listing_facts > data/dumps/flatplanner-data.sql
```

1. Railway → MySQL service → Settings → Networking → Public Access. A TCP proxy and a `MYSQL_PUBLIC_URL` variable with the host and port are created.
2. Clear the tables (the schema already exists from migrations):
   ```bash
   docker compose exec -T -e MYSQL_PWD="$PROD_MYSQL_PASSWORD" mysql mysql -h <proxy-host> -P <proxy-port> -u root <MYSQLDATABASE> -e "SET FOREIGN_KEY_CHECKS=0; TRUNCATE listing_facts; TRUNCATE listings; SET FOREIGN_KEY_CHECKS=1;"
   ```
3. Import:
   ```bash
   docker compose exec -T -e MYSQL_PWD="$PROD_MYSQL_PASSWORD" mysql mysql -h <proxy-host> -P <proxy-port> -u root --default-character-set=utf8mb4 <MYSQLDATABASE> < data/dumps/flatplanner-data.sql
   ```
4. Check: `SELECT COUNT(*) FROM listings;` (= local) and `SELECT district_name FROM listings WHERE district_name LIKE 'Ś%' LIMIT 3;` (Polish characters).
5. Turn off Public Access.

`__EFMigrationsHistory` is not transferred.

### 11.5 Smoke test on production (`$URL` = the public address)

1. `curl -s $URL/api/health`: `db: ok`, `clientIp` = your public IPv4 (compare with `curl -4 -s ifconfig.me`); repeat from another network; a request with a forged `X-Real-IP` must still show your own address.
   Run the smoke test after the last data import: the chat schema contains the district list, so the first LLM call after an import may be slower (step 3 doubles as a warm-up).
2. **Scenario A:** `curl -s "$URL/api/listings?cities=gdansk&areaMin=40&areaMax=80" | jq '.total, .items[0].id'` → total > 0. Then `curl -s $URL/api/listings/<id> | jq '.fields.pricePln, .askSeller'`. In the browser: filter → district → sort by price/m² → details → “back” preserves the filters.
3. **Scenario B:**
   ```bash
   curl -s -X POST $URL/api/search/interpret -H 'content-type: application/json' -d '{"message":"chcę ładne, tanie mieszkanie, 40 m w Gdańsku"}' | jq
   ```
   Expected: `usedFallback: false`, `areaApprox: 40`, both preferences. Then GET with this intent → `sort: relevance`, `why` non-empty.
4. **Text search:** `curl -s "$URL/api/listings?cities=gdansk&text=morena" | jq '.total'` → the listed items contain „morena” in the title, description or street.
5. **Kraków:** `{"message":"2 pokoje w Krakowie"}` (2 rooms in Kraków) → `requestedCityOutOfScope: "Kraków"`, `cities: ["gdansk"]`.
6. **Protection:** 6 interpret requests in a minute from one IP → the sixth gives 429.
7. **Response shape:** `curl -s "$URL/api/listings?cities=gdansk" | grep -c ':null'` → `0` (the serialization rule from §6 works over HTTP, including `TypedResults`). `curl -sI -H 'Accept-Encoding: br, gzip' "$URL/api/listings"` → `content-encoding` present (by the Railway proxy or by our middleware, §6).


### 11.6 CI and CD

**CI** (`.github/workflows/ci.yml`, on `pull_request` and `push` to `main`, two parallel jobs, no secrets, no database, no LLM):
- **backend:** `actions/setup-dotnet` with the version from `global.json` → `dotnet restore` → `dotnet format --verify-no-changes` → `dotnet build --no-restore` → `dotnet test --no-build`;
- **frontend** (`working-directory: web`): `actions/setup-node` with Node 22 (react-router 8 requires ≥ 22.22) and the npm cache → `npm ci` → `npm run lint` → `npm run build` (includes `tsc`).

The `main` branch requires both jobs to pass before a squash merge. A `docker build` job is not added: the Dockerfile is exercised by every Railway deploy, and a broken image is visible in the deploy log within minutes.

**CD:** no deploy workflow. Railway deploys every push to `main` from its GitHub integration; enable the service option that waits for GitHub checks before deploying, so a red build never reaches production. Migrations run at startup (11.3).

## 14. Resolutions and decisions

### 14.1 Resolutions of ambiguities

Places where earlier documents or data allowed two variants, and the variant adopted in this design.

| # | Issue | Resolution | Reason |
|---|---|---|---|
| R1 | chat endpoint: `POST /api/search/chat` returning results or `POST /api/search/interpret` returning the intent | `POST /api/search/interpret` returns only the intent; results always from `GET /api/listings` | a single results path for the form, chat, chips and “back”; the interpretation line is computed by code from the intent, so it comes from GET. Rejected: results in the chat response (two paths building the list and state outside the URL). Cost: 1 extra request ~20 ms |
| R2 | URL parameter names: `?city=gdansk` or the `SearchIntent` field names | URL parameters = `SearchIntent` field names (`cities=gdansk`) | one name for the same thing in C#, JSON, URL and TS; the agent does not need a mapping table |
| R3 | range for “40 m” with a ±12% tolerance: rounding of the bounds | `floor(a×0.88)`–`ceil(a×1.12)`, i.e. 35–45 | one rule in code instead of manually computed examples |
| R4 | parking status with no surcharge and with no parking: `none` or `not_available` | `not_available` in the database and `not_mentioned` only in the LLM response | `none` is confused with “no data”; an explicit “not mentioned” option reduces fabrication |
| R5 | data provenance: `*_source` columns per field (a variant for UC15) | provenance as a field constant (3.4) | within the scope no field has two sources |
| R6 | [scraping-plan.md](scraping-plan.md) §4: “bool flags” of amenities; alternatively three-state yes/no/no information | `TRUE`/`NULL` + CHECK, two-state “yes / no information” | `Extras_types` is a list, a missing element ≠ “no”; confirmed in 14 listings: `additionalInformation.lift` = `::y` or an empty array |
| R7 | [product-scope.md](product-scope.md) §0: `Rent="0"` (string) | the parser accepts a number and a string | in `target` `Rent` is a number (`0`, `700`), in `characteristics` a string |
| R8 | [product-scope.md](product-scope.md) §2: the name of the ground floor unconfirmed | `ground_floor` → 0; `cellar` → −1; `garret` → NULL + flag | `ground_floor` is visible in the data; `cellar`/`garret` occur as tokens on otodom pages |
| R9 | [scraping-plan.md](scraping-plan.md) §1, §4: advertiser “developer” | `agency`/`private` | in 14 listings (including primary-market ones) only these two values |
| R10 | [scraping-plan.md](scraping-plan.md) §7: raw HTML (gzip), carrier classification, circuit breaker | raw `ad` JSON without contact data + hard-field contract + report | one-off import ([product-scope.md](product-scope.md) §0) |

| R15 | data scope | Tricity (Trójmiasto), scenarios on Gdańsk; Kraków outside the data (UC13) | several cities and many districts give sensible filters and medians ([scraping-plan.md](scraping-plan.md) §2) |
| R16 | LLM provider (the task requirements allow any) | OpenAI | credits available on the OpenAI account |
| R17 | [product-scope.md](product-scope.md) §4 item 4: text search = `LIKE` alone | adopted: filters, `LIKE` text search and chat (LLM); keyword parsing of the search field cut (6.7) | the requirement “text + filters” is met by `LIKE`; parsing intent from text is the chat's job, so a second parser would duplicate it |
| R18 | response shape of the list: full echo of the intent with every `null`, a separate `cityMedians` field, `remove` as a list of `{param, value}` | no intent echo in `GET /api/listings`, `null` fields omitted (except `Sourced<T>.Value`), no `cityMedians`, `remove` as a map | an echo nobody reads, three copies of the median and `null` sentinels make the response harder to read without adding information; transfer size is handled by compression (§6) |

Facts return with the dossier (#11′) |

## 16. AI-first pivot (2026-11-05)

**Why.** Portal filters cover only the fields the source happens to have, so the buyer still reads listing after listing to find what matters to them. The product's core value is: **the user states any need in their own words, and AI judges every listing against it**, using data no filter holds: the description, the structured fields and the surroundings of the flat. There is no catalog of criteria and no mapping to categories. Every verdict carries evidence that code checks (a quote, a nearby place, a field). This section supersedes the parts of sections 5, 6, 7, 9, 12, 13 and 14.4 it names; where it is silent, the earlier sections apply.

**The rule changes from "the model translates, code decides" to "the model judges, code verifies".** The model decides whether a listing fits; it cannot invent the reason, because every reason must point at evidence present in the listing's dossier, and code rejects any that does not.

**Measured on the local import (197 listings, 2026-11-05):**
- `kredyt` (mortgage) appears in 81 descriptions, ~77 of them only as agency boilerplate; the listing-level facts (clean land register in 7, a bank mortgage repaid from the price in 1) need reading, not matching.
- `cisza`/`cich` (quiet): 50 descriptions, 13 only because of "cichobieżne windy" (quiet lifts). `zwierz`/`kot` (pets): 20 hits, all "kotłownia" (boiler room).
- No description mentions an Orthodox church or a synagogue, but all 197 listings have `lat`/`lng` (83 approximate). OSM has the Orthodox church of St Nicholas and the New Synagogue in Gdańsk: 8 listings within 1 km of the church (all approximate), listing 97 at 148 m from the synagogue.
- Morena (Piecki-Migowo): 6 listings, all within 750 m of an OSM `amenity=school`, but for two of them the nearest one is a post-secondary school; all 6 are `full_ownership`, none mentions foreign buyers.

### 16.1 Import: the listing dossier (replaces mini-W2, section 5)

The dossier is built once, locally. **The language part is done by a coding agent working from the versioned prompt, not by paid API calls** (agreed 2026-11-05): it is a one-off over ~200 listings, the output is validated by code exactly as an API response would be, and the API key is then needed only at runtime (`ask`) and for `eval-intents`.

Per listing:
- `ai_summary VARCHAR(1000) NULL`: 2-3 Polish sentences about the flat itself; agency boilerplate (financing help, commission, disclaimers) ignored.
- `risks_json JSON NULL`: buyer risks that do not depend on any question: `[{ "kind", "reason", "quote", "amountPln"? }]`, `kind` ∈ `extra_cost` (parking, garage or storage paid on top, incl. obligatory ones), `legal` (commercial premises with VAT, bankruptcy-trustee sale, garage on a separate land register, bank mortgage repaid from the price), `occupied` (rented out), `noise` (a named source: clubs, concerts, a planned tram line), `field_mismatch` (a field contradicts the description: rooms, area, floor, building floors, lift, rent, market, heating, finish condition, ownership, garage, advertiser type; a developer selling directly is not an advertiser-type mismatch, because otodom lists developers as `agency` (R9), and a garage paid on top is `extra_cost`, not a garage mismatch, because `has_garage` says only that one exists). A description's claim is a declaration, not proof: "wyjątkowo ciche" on a main street is reported as a contradiction, not repeated.
- `nearby_json JSON NULL`: places within 1 500 m from OpenStreetMap, fetched once with a single Overpass query over the bounding box of all listings plus 1 500 m (`https://overpass-api.de/api/interpreter`, `User-Agent` set; one query per listing was the first plan, but overpass-api.de cools each of its 2 slots per IP for ~40 s, so 197 queries took ~2.5 h): `amenity` in {school, kindergarten, place_of_worship, pharmacy, clinic, hospital, doctors, university, veterinary, bar, pub, nightclub, restaurant, cafe, charging_station, bicycle_rental}, `leisure` in {park, playground, dog_park, fitness_centre, sports_centre, swimming_pool, stadium}, `natural` in {wood, beach}, `landuse` in {forest, cemetery}, `railway` in {station, halt, tram_stop}, `highway=bus_stop`, `shop` in {supermarket, convenience, mall}; and as lines (noise sources) `highway` in {motorway, trunk, primary} and `railway` in {rail, tram}. The second group of kinds was added after checking coverage on the import (listings with one within 1 500 m): beach 79, primary road 146, rail line 141, bar/pub 99/115, charging station 174, bike rental 197; each answers a buyer need the first list could not (sea, quiet, night life, EV, cycling, pets, sport). Industrial land, water and theatres were left out: small industrial polygons and ponds are everywhere, culture venues reach too few listings. Two more entry groups answer "how far" and "how do I get there": **landmarks** kept at any distance (the nearest beach, train station or halt, hospital and airport with an `iata` code, and the `place=city|town` centre of Gdańsk, Gdynia and Sopot, from a second query with a 20 km margin), and **transit lines** from OSM route relations (`route` in {bus, trolleybus, tram, train, light_rail}): one entry per line whose stop or platform is within 500 m, `{ "n": "N2: Brętowo → Dworzec Główny", "t": "route=bus", "x": "ref=N2", "d": metres to the nearest stop }`, both directions merged. Night lines are the `N…` refs; 2026-11-06 OSM had 363 bus, 48 tram and 33 train routes in central Gdańsk alone. So `d` is ≤ 1 500 m except for landmarks. Stored as `[{ "n": name, "t": "amenity=school", "x": "isced:level=1;religion=…", "d": metres }]`, distances by haversine in C#. Kept: the 3 nearest per (`t`, `x`), so a Catholic church does not push out an Orthodox one and a post-secondary school does not push out a primary one. The first plan, the nearest 60 overall, filled up with unnamed woods and playgrounds: a listing has ~270 places within 1 500 m, the 60th was at a median of ~590 m, and no listing kept the Orthodox church of St Nicholas (9 within 1 500 m with the per-kind cap).

Ingest commands (replace `enrich` from section 5):

| Command | Action |
|---|---|
| `nearby` | Overpass → `nearby_json` for listings where it is NULL |
| `export-dossiers` | writes `data/agent/listings.jsonl`: `externalId`, fields, `description_text` (gitignored like all of `data/`) |
| *(agent)* | reads `prompts/listing-dossier.v2.md` and `listings.jsonl`, writes `data/agent/dossiers.jsonl`: `{ externalId, summary, risks[] }` |
| `import-dossiers` | validates and writes `ai_summary`, `risks_json`, `facts_status` |

`import-dossiers` validation (same rules as for a model response, section 5.1): `externalId` must exist; `summary` 1–1 000 characters; each risk: `kind` from the list, `quote` a substring of the description after `AnchorText.Normalize`, `amountPln` only for `extra_cost` and equal to a number extracted from the quote (5.1 number rule, range 5 000–300 000). An invalid risk is dropped and counted; a listing without a valid line gets `facts_status = 'failed'`. The `report` prints accepted and dropped risks per kind; the dropped share is the honesty metric for the agent's output. `prompt_version` (`listing-dossier.v2`) and the producer (`agent`) are printed in the report and stated in the README.

Implementation details (#11′): `AnchorValidator.Validate(risk, normalizedDescription)` returns a reject reason in this order: `unknown_kind`, `missing_reason` (empty `reason`), `missing_quote`, `quote_not_found`, `amount_not_allowed` (`amountPln` on a kind other than `extra_cost`), `amount_not_in_quote`, `amount_out_of_range`. An invalid line (not JSON, unknown or duplicate `externalId`, invalid `summary`) is logged and counted. The `report` re-runs the same validation over `data/agent/dossiers.jsonl` when the file exists, so dropped risks need no column; it also prints the `nearby_json` fill and the `facts_status` counts. `nearby` keeps the nearest element per (name, tag) for named places (bus and tram stops come in pairs), `x` carries `isced:level`, `religion` and `denomination` when present, an unnamed place has no `n`, and the distance of a way or relation is measured to the nearest point of its bounding box (`out center bb`), so a large forest counts from its edge, not its centre; roads and tracks are fetched with `out geom` and measured to the nearest segment, because a long road's bounding box covers half a district, and an unnamed line keeps only its nearest segment; a place is kept when that distance is ≤ 1 500 m. A failed Overpass request is logged and leaves `nearby_json` NULL for the next run. `listing-dossier.v2` replaced v1 after the first run over all 197 listings: 63 of v1's 99 `field_mismatch` risks were false (a developer flagged as an advertiser-type mismatch, a paid parking space flagged as a garage mismatch next to its own `extra_cost` risk). `nearby` waits 30 s and retries up to 5 times on HTTP 429/504 (busy slots). `normalize` keeps `ai_summary` and `risks_json` unless the description changed, and `nearby_json` unless the coordinates changed.

Migration `AiDossier` adds the three columns. Overpass and the agent are never part of the API; the data reaches production with the dump (11.4). `listing_facts`, `AnchorValidator` amount rules beyond the above and the import-time real price (5.3) are cut; the real price is computed at query time from verified `extra_cost` risks (16.2 step 7).

### 16.2 `POST /api/search/ask` (replaces `POST /api/search/interpret`, 6.3)

Request `{ "message": string, "excludeNeeds": int[] }` (message 1–300 characters; `excludeNeeds` optional, indexes into the interpreted `needs`). The query string optionally carries the filter parameters of `GET /api/listings` (6.1; `sort` and `page` are ignored): after the cached evaluation the candidates are narrowed to those passing `ListingFilters.Apply` with the normalized filter intent, and groups, counts and relaxations are computed from what is left (R26). One endpoint does the whole pipeline; the frontend keeps only `?q=<message>` in the URL, and the response cache makes refresh and "back" free.

1. **Interpret** (`prompts/search-intent.v2.md`, structured output): hard filters from `SearchIntent` (only `cities`, `districts`, `priceMax`, `areaMin`, `areaMax`, `roomsMin`) plus `needs: string[]` (max 4, each one restated in Polish: "podstawówka w zasięgu spaceru dla 7-latki") and `declined: [{ text, reason }]` for requests the system will not judge (16.4). "dom" means a place to live unless a house is named explicitly; "bez kredytu" is context, not a need.
2. **Narrow** (C#): SQL with the hard filters → candidates (≤ 197). When the question has needs and more than `ListingJudge.MaxCandidates` (40) listings match, only the 40 newest (`created_at_source`, then `id`) are judged and the rest is not shown; a `judge_limited` notice says so (cost cap, 16.7).
3. **Judge** (`prompts/listing-judge.v1.md`; input trimmed per need by 16.8): batches of 15 dossiers (id, fields, `ai_summary`, `description_text` truncated to 8 000 characters (3 000 cut 52 of 197 descriptions, the longest is 7 687; what a seller writes late, such as pets, orientation or air conditioning, would be lost), `nearby_json` reduced to the nearest place per (`t`, `x`) with its original index, `location_approximate`), all batches at once (`SemaphoreSlim(14)`, the ~200 listings make at most 14 batches). Output per listing: `{ id, needs: [{ verdict: "yes"|"partly"|"no"|"unknown", reason, evidence: [{ kind: "quote"|"place"|"field", ref }] }] }`. Risks are not judged at runtime: they come verified from the dossier (`risks_json`, 16.1) and are attached to every item by code. **The judge treats a description's claim as a declaration, not as proof:** "wyjątkowo ciche" on a main street is checked against the nearby places and the location.
4. **Verify** (C#, `EvidenceVerifier`): `quote` must be a substring of the description after `AnchorText.Normalize`; `place` must be an index into that listing's `nearby_json`; `field` must name a listing column. A `yes`/`partly`/`no` without valid evidence becomes `unknown`. Unknown ids are dropped. `location_approximate = true` turns a `place`-only `yes` into `partly` with the note that the location is approximate.
5. **Group and order** (C#), `group` per listing:

   | `group` | Condition | Shown |
   |---|---|---|
   | `full` | every need `yes` | first |
   | `partial` | at least one `yes`/`partly`, no `no` | second |
   | `near` | exactly one `no` (with valid evidence) | third, the failing need highlighted: "Prawie pasuje: jedna rzecz nie gra" |
   | `unknown` | only `unknown` verdicts | collapsed, count in `unknownCount` |
   | — | two or more `no` | hidden |

   Within a group: more `yes`, then fewer `unknown`, then newest. With one need, `near` is empty by definition (one `no` = does not fit).
6. **Relaxations** (C#, no LLM call): when `full` is empty, `relaxations` lists for each need how many listings would be `full` or `partial` without it, from the verdicts already computed: `[{ need, count, bestId }]`, descending by `count`, only `count > 0`. The UI offers "Pokaż bez tego warunku"; the click re-sends the same message with `excludeNeeds: [index]`, served from the cache without a model call. When step 2 already returns no candidates, `relaxations` lists instead each hard filter removed separately with its `COUNT` (at most 6 queries, the logic of 6.4 limited to the `ask` hard filters), and no judge call is made.
7. **Real price for extra costs:** for `extra_cost` risks in `risks_json` with `amountPln` (already checked against the quote at import), code adds `totalWithExtrasPln = price_pln + Σ amountPln`. The model never computes amounts.

**Contract details (#7′a, agreed 2026-11-06):**
- Interpret output (`AskIntent` in Core, schema `search_intent` from `SearchIntentSchema.Build(meta)`): `cities`, `districts`, `priceMax`, `areaMin`, `areaMax`, `roomsMin`, `needs` (code keeps the first 4), `declined: [{ text, reason }]`, `clarifications: string[]` (at most 2 model-written Polish remarks: an inconsistent need, 16.4, or a city we do not have). "ok. 40 m" becomes the 7.4 range in the prompt; the fallback parser keeps only the rules for these filters (`IntentFallbackParser`, `FallbackDictionaries`; `KeywordRules` and the rest of the 7.7 table are not built).
- `summary` is built by code: the hard-filter chip labels (`InterpretationBuilder`) and the `needs`, joined with ` · `.
- `notices: [{ code, text }]`: `clarify` (each `clarifications` entry), `judge_limited` (step 2: "Oceniliśmy {n} najnowszych z {m} ogłoszeń. Zawęź miasto, dzielnicę lub cenę, żeby sprawdzić resztę."), `ai_unavailable` (interpret fallback, ui-spec 11.3), `judge_failed` (a judge batch failed, ui-spec 11.3). The response carries `fallbackReason` (7.7 values) when `usedFallback`.
- Item: `id`, `title`, `pricePln`, `areaM2`, `rooms`, `floor?`, `buildingFloors?`, `cityName`, `districtName?`, `imageUrl?`, `aiSummary?`, `locationApproximate`, `group`, `needs`, `risks: [{ kind, reason, quote, amountPln? }]` (from `risks_json`), `totalWithExtrasPln?`. The approximate-location note is shown by the UI from `locationApproximate`.
- `needs` always lists every interpreted need, so `excludeNeeds` indexes stay stable; excluded needs are skipped only by grouping and relaxations. Items keep a verdict per need.
- A verdict downgraded to `unknown` loses its `reason` and `evidence` (an unverified reason would still assert the claim). Evidence labels: a quote as cited (after the substring check), a place as "{name} · {d} m" with the ui-spec 11.3 tag name for an unnamed place, a field as "{ui-spec 7.2 label}: {value}". Allowed `field` refs are the fields sent to the judge (the 7.2 detail fields with a value; `buildingFloors` resolves to the floor label).
- Hard-filter relaxations (no candidates): `{ need: <chip label>, count }` without `bestId`; informational, because the request has no parameter that removes a hard filter.
- Judge: batch timeout 60 s (constant `ListingJudge.Timeout`, covers 1 SDK retry), effort `LLM_CHAT_REASONING_EFFORT`, `MaxOutputTokenCount = 8192`, `ref` is a string (a place is its `nearby_json` index). Only fully successful answers (no fallback, no failed batch) are cached.

**Failures (never 5xx):** interpret fails → `IntentFallbackParser` (7.7) for hard filters, `needs: []`, `usedFallback: true` with `fallbackReason`; judge fails for a batch → its listings get `unknown` and a notice. `400` for an empty or > 300 characters message, `429` from the rate limiter (section 8, also counts `ask`).

**Cache:** in-memory dictionary keyed by the folded message, process lifetime. **Cost (superseded by 16.7: cap of 40 candidates, own judge model):** a new question ≈ 14 judge calls × ~20k input tokens ≈ $0.3 and 5–10 s with the section 5.2 prices **[estimate]**; the UI shows a progress state. Measured on the local import (2026-11-06): a dossier averages ~6 200 characters of `nearby_json` (89 places, max 12 900) and ~2 400 of description, so a batch of 15 is ~45k input tokens and a question ~630k (~$0.6) **[estimate, to be checked on the first live run]**.

**Judge latency (measured 2026-11-06, `gpt-6.1-terra`, effort `none`):** the first run with `SemaphoreSlim(4)` and a 30 s batch timeout took 123 s for a message without filters (197 candidates, 14 batches), and 11 of 14 batches timed out: a batch of 15 listings × 3 needs takes ~30 s, bound by output tokens, so only running batches in parallel shortens the wall time. Changed to all batches at once and a 60 s timeout; the judge gets only the nearest place per (`t`, `x`) (89 → 48 places, ~6 900 → ~4 000 characters per listing), which lowers input tokens by ~30% and keeps every kind, every transit line and every landmark. The progress state in the UI is sized for ~30–60 s. All 14 batches at once send ~450k input tokens within a minute, so the OpenAI project's TPM limit must allow it; a 429 is retried once by the SDK and then becomes a failed batch.

### 16.3 Domain knowledge the judge may use

`prompts/listing-judge.v1.md` contains a short, versioned list of rules the model may apply, each with the field it rests on:
- a buyer from outside the EEA in Gdańsk, Gdynia and Sopot (border zone) needs an MSWiA permit for `ownership = full_ownership`, not for `limited_ownership` **[TO VERIFY: act on the acquisition of real estate by foreigners, art. 8]**;
- a bank financing a purchase expects a land register without encumbrances;
- an `amenity=school` with `isced:level` other than 1, or a name containing "policealna"/"liceum", is not a primary school;
- `ownership = limited_ownership` (cooperative ownership right) is what lets a foreigner buy without the permit; when the field says `limited_ownership` and the description is silent about the kind of right, the verdict is `partly` with "zapytaj o rodzaj prawa" **[TO VERIFY]**;
- commercial premises sold with 23% VAT are not a flat: the tenant-protection act and residential mortgage terms may not apply **[TO VERIFY]**;
- a sale by a bankruptcy trustee (syndyk) requires a deposit, usually without a viewing, "as is"; mortgage financing is harder **[TO VERIFY]**;
- a flat sold with a running lease is not available until the lease ends;
- a garage on a separate land register is a separate purchase with its own price and its own mortgage question **[TO VERIFY]**.

These rules come from general knowledge, not from the data; each stays marked until checked, and the 1-pager says so.

Anything outside these rules and the dossier is `unknown`.

### 16.4 Guardrails

- The system judges flats and places, never people: no verdicts on who lives in an area ("tolerancyjna okolica", "bez obcokrajowców"). Such parts go to `declined` with a reason, and the model proposes checkable needs instead (e.g. "blisko centrum, komunikacja nocna").
- Personal traits the user mentions are context: not stored, not logged (7.7). They influence a verdict only through a rule in 16.3 (citizenship → permit).
- If the stated need and the context look inconsistent (Jewish + Orthodox church), the need is judged as stated and a notice asks whether a synagogue was meant.

### 16.7 Cost of one question (2026-11-06)

First live measurements: ~$0.5 and several minutes per new question with `gpt-6.1-terra` ($1 / $5 per 1M tokens, 14.2) and all 197 listings. Local measure of what one listing sends to the judge: `nearby_json` 6 159 characters (~3 400 after the nearest-per-kind trim), `description_text` 2 546, `ai_summary` 481, fields ~400; ~2 000 tokens per listing, ~400k input tokens per question, plus ~30k output tokens (the output is the larger share of the latency). Decisions:
- **Candidate cap:** 40 listings per judged question (16.2 step 2): ~80k input tokens, about 5 times fewer than before.
- **Own model for the judge:** `LLM_JUDGE_MODEL` (empty = `LLM_MODEL`), so the judge can run on a cheaper model (`gpt-6-luna`, $0.10 / $0.50, accepts effort `none`) while the interpretation stays on `LLM_MODEL`. Quality on Polish nuances (14.2) is checked by reading the verdicts of the demo listings before the model is changed in production.
- **`needs` last in the judge input:** the listings form a repeating prefix, which the API caches automatically for identical batches.
- **Usage log:** every LLM call logs input, cached and output tokens (`LLM call {Schema}: …`), so the cost of a question is summed from the log.
- **Planner per need:** first rejected here (one more prompt, schema and failure path for ~25% of the input). Superseded by 16.8: the planner rides in the existing interpret call, so it adds no call and no failure path, and live use still shows ~$0.5 per new question, which makes the judge input as the cost to cut.

### 16.8 Judge context per need (2026-11-06)

A judged listing sends ~6 800 characters (~2 400 tokens; measured on the 40 newest local listings): `nearby` ~3 500 (43 places of every kind, route entries with full stop-to-stop names), `description` ~2 400, `aiSummary` ~440, `fields` ~400. A question about a school reads a few hundred of them. Goal: cut the judge cost of a new question by about two orders of magnitude without weakening the evidence rule (16.2 step 4).

1. **Need plan from the interpret call** (`prompts/search-intent.v3.md`, no extra call). `needs` in the interpret output becomes `[{ text, places, keywords }]` (`AskNeed` in Core):
   - `places`: OSM tags the need is checked against, a strict-schema enum of the `PlaceLabels` tags (`PlaceLabels.AllTags`, passed to `SearchIntentSchema.Build`): "podstawówka w zasięgu spaceru" → `amenity=school`; "cisza w dzień" → `highway=primary`, `highway=trunk`, `railway=tram`, `railway=rail`;
   - `keywords`: at most 6 Polish word stems that a sentence of the description about this need would contain ("cich", "spokoj", "hałas", "okn"); code folds them (`TextFolding.Fold`), drops stems shorter than 3 characters and keeps 6 (`SearchDefinitions.MaxNeedKeywords`, `NeedKeywordMinLength`; `IntentInterpreter.Clean`).
   The response keeps `needs: string[]` (the `text` values), so the UI, `excludeNeeds` and the cache are unchanged.
2. **Judge input built by code** (`JudgeInput`, pure functions over a candidate and the need plans):
   - `nearby`: the nearest place per (`t`, `x`) only for tags named by some need, original `nearby_json` index kept (the verifier resolves `place` refs against it); `route=*` entries lose `n` (the stop-to-stop name), `x` keeps the line `ref`;
   - `fields`: all of them as before (~400 characters; planning them would add an enum for ~5% of the old input);
   - `description`: only the sentences (split on `.`, `!`, `?` and line breaks) whose folded text contains a folded keyword of some need, verbatim and in their original order, so `quote` refs stay substrings of the description;
   - `aiSummary` is not sent (the prompt already forbade it as evidence);
   - a need with an empty plan (no places and no keywords) makes the input the full 16.2 step 3 dossier without `aiSummary`, so a need the planner cannot place loses nothing.
   The listings are no longer a prefix shared between questions, so the "`needs` last" prompt-cache note of 16.7 no longer applies; the response cache (16.2) is unchanged.
   Simulated on the 40 newest local listings: school + quiet + MSWiA ~1 100 characters per listing, dog walks ~600, night transit ~1 400, against ~6 800 before.
3. **Shorter output** (`prompts/listing-judge.v2.md`): 1–2 evidence items, `reason` at most ~15 words. Output tokens cost 5× input (14.2).
4. **Small model for both calls:** `LLM_MODEL` and `LLM_JUDGE_MODEL` default to `gpt-5.6-luna` (decided 2026-11-06, before the verdict check; supersedes the 14.2 choice of `gpt-6.1-terra`); an empty `LLM_JUDGE_MODEL` still falls back to `LLM_MODEL`. The interpretation carries the need plan every later step depends on, so its needs, places and keywords are read on the 16.6 scenarios too, and its latency must fit `CHAT_TIMEOUT_SECONDS` with the longer output (the first terra run timed out twice at 5 s) **[TO VERIFY on the first run]**. The verdicts for the demo listings (16.6: 70, 97, 166) are read against those of `LLM_MODEL` on the 16.6 scenarios and recorded here; effort `none` must be accepted by the model **[TO VERIFY on the first run]**.

**Fallbacks:** unchanged. Interpret failure gives `needs: []`, so there is no judge call; the `places` enum is strict, so an unknown tag cannot arrive.

**Not built:** verdicts computed by code for "place X within N m" needs. Code would write the Polish `reason`, and ui-spec §7 has no such strings; with the trimmed input on the small model the judge call is already ~$0.01.

**Tests (§12):** `JudgeInputTests`: nearby limited to the planned tags with original indexes, route names dropped, sentences selected by folded keywords in their order, no match gives an empty description, an empty plan gives the full dossier. `SearchIntentSchemaTests`: the `places` enum, need deserialization, keyword cleaning.

**Definition of done:** the judge input averages ≤ 600 tokens per listing in the `LLM call` log over the 16.6 scenarios **[TO VERIFY on the first run]**; the demo scenarios (16.6) give the same groups as before on listings 70, 97 and 166; a new question costs ≤ $0.02 by the usage log; tests green.
